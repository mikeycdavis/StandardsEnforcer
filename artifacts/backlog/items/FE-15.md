> was accurate against the pre-`31fb5ec` implementation and is **superseded, not deleted**. Keeping
> it visible is the point: the failure mode changed, and that change is the most useful thing here.
>
> **The current defect, stated in one sentence:**
>
> > Cross-process use of the same shared cache root can cause one verified run to invalidate another
> > run's entry mid-use, producing a **false negative** rather than false assurance.
>
> **This is no longer a false-assurance defect.** The security property held — the second process
> refused to execute bytes whose identity it could not establish. What failed is operational
> isolation and determinism under concurrent use. The remedy must therefore target determinism
> *without* weakening the identity boundary, and hardening that boundary further would be aiming at
> the part that worked.
>

## What

Every suite that materialises a standards identity derives its cache root from `tmpdir()` with a
fixed name:

```js
const CACHE = path.join(tmpdir(), "standards-enforcer-test-cache");   // enforce, gate, scope
const CACHE = path.join(tmpdir(), "enforcer-provenance-cache");       // adapter-provenance
```

`node --test` runs test **files** in parallel. Those files therefore populate, read, assert over and
delete the same directories at the same time. The names are fixed per file rather than per run, so
two concurrent runs of the same suite — two sessions, two worktrees, or CI and a workstation sharing
a machine — collide as readily as two files in one run.

## Why

**The suite is non-deterministic, and its failures are indistinguishable from real defects.**
Observed across consecutive parallel runs of the same tree at `29510e3`:

```text
run 1   12 failures
run 2    4 failures
serial   0 failures      (--test-concurrency=1, 165 pass, 1 skipped)
alone    0 failures      (each affected file, run by itself)
```

Two shapes: `ENOTEMPTY` when one file removes a directory another is writing, and cache-listing
assertions observing entries a different file created.

**This is a false-assurance risk in both directions.** A red run invites the reading *"flaky, re-run
it"*, which is how a real regression gets waved through; a green run proves less than it appears to,
because whether a given assertion saw its own cache state or another file's is a matter of timing.

**Newly consequential, and not newly caused.** [FE-14](FE-14.md) made CI execute the oracle-dependent
tests that previously vanished behind skips. Those are the tests that materialise identities, so the
contention now reaches a gate that used to never run. FE-14 exposed this; it did not cause it, and
the two must not be folded together.

## Notes

**Found 2026-08-12** while mutation-checking FE-14 — twice over, since a second session was
concurrently running the same suites against the same `tmpdir` roots. That accident is worth keeping:
it is the clearest demonstration that the fixed names are the defect, because nothing about either

**Independently reproducible**, and reproducible without a second session: repeated `node --test`
runs on one machine produce different failure sets.

## Acceptance property — a product property, not a suite property

Governed by [ADR 0006](../../adr/0006-the-cache-is-shared-and-coordination-is-not-authority.md).
~~Concurrent test files must not share mutable cache roots…~~ — struck, because it named the
discovery path as the defect. Concurrent processes sharing the cache are **supported**, so the suite
sharing a root is fidelity to the real invocation model, not a test smell.

> **Two independent StandardsEnforcer processes using the same shared cache root for the same release
> identity must both complete deterministically, neither executing unverified bytes, and neither
> invalidating the other's verified use.**

The item stays under EP-01: this is the epic that owns identity and materialisation, and the defect
is in `scripts/identity.mjs`, not in the harness. The test flakiness remains attached as the
**discovery path**.

## Falsifier — two arms, and the second is the one that matters

```text
ARM 1 — the race
  two independent processes
  → same shared cache root
  → same release identity
  → one process causes repair / materialisation pressure
  → both complete deterministically
  → neither executes unverified bytes
  → neither invalidates the other's verified use

ARM 2 — the negative control
  a verified entry is actually tampered with
  → coordination must NOT preserve trust
  → re-verification detects it
  → enforcement refuses or repairs
```

**Arm 2 exists because a lock-only implementation can make the race disappear while restoring stale
trust.** If holding the lock ever becomes a reason to skip verification, arm 1 goes green and the
product is back to `.enforcer-complete` under a new name. ADR 0006 rule 5 is normative for exactly
this reason: *coordination decides who may write; verification decides what may run.*

**Third arm, on granularity:** two **different** SHAs must still materialise **concurrently**. An
implementation that satisfies arm 1 by serialising all materialisation passes the letter of the
contract and defeats the reason it is scoped per identity.

## Constraints carried forward

- **Provenance case 9 keeps a deliberately shared root.** *Two identities never share a
  materialisation* is a test **about** sharing; a remedy that privatises every root deletes the
  condition it exercises.
- **Not `--test-concurrency=1`.** It hides the defect, does nothing for the cross-process case that
  *is* the defect, and abandons the parallel execution under which the guarantees are claimed.
- **Not per-worktree or per-session cache roots.** That changes the product contract rather than
  fixing the product, and makes the suite stop modelling production.
- **A lock that can go stale must fail toward uncertainty**, never toward trust, and must be
  recoverable by taking it and re-verifying.

## Superseded proof

```text
before:
  node --test, repeated
  → nondeterministic ENOTEMPTY and cross-file cache observations

after:
  node --test, repeated, parallel
  → deterministic
  → the same behavioural assertions as serial execution, not fewer
```

Struck 2026-08-12: the "before" half no longer reproduces, and the "after" half is already true —
three consecutive parallel runs are deterministic and green. Retained because the change in failure
mode is the finding.

Both arms are required. The second is the one that catches the tempting fix: a change that isolates
by removing or weakening the assertions that observe cache contents would produce a green
deterministic suite that proves less than the flaky one did. **Assert that the post-fix suite runs the
same tests as the serial run** — same count, same names, same skips — and that provenance case 9 still
exercises a genuinely shared root.

## Sequencing

~~Do not start while the D2/[FE-13](FE-13.md) work is in flight.~~ **Unblocked 2026-08-12:** FE-13 is
`COMPLETE` and integrated at `c3cb08e`.

**The reproduction above is no longer authoritative and must be re-run before any remedy is
designed.** `31fb5ec` changed the mechanism this item was written about:

- the completion marker **moved out of the checkout**, so the cache directory's contents and its
  bookkeeping are no longer the same tree;
- repair stages to **`.staging-<sha>-<pid>`** and renames, rather than deleting in place —
  explicitly *"staging is per-process, so two runs repairing the same identity cannot collide
  mid-clone"*, which addresses part of this defect from a different direction;
- every cache hit now re-verifies and a failed entry is discarded and rebuilt, which changes what a
  concurrent observer sees mid-run.

FE-13 also names what it did **not** close, and it lands squarely here: **concurrent repair has no
cross-process lock.**

**Re-run 2026-08-12. Result: narrowed, not gone.** Three ordinary parallel suite runs are now
deterministic and green — the intra-run contention is solved by per-process staging. Two *concurrent
suite processes* still reproduce it, as one failure, `STANDARDS_IDENTITY_MISMATCH` where `EVALUATED`
was expected.

## The design question, which this item cannot answer by itself

> **Is a cache root intended to be shared safely across independent StandardsEnforcer processes?**

Answer it from the cache contract, the ADRs and the actual invocation model — **not** from what would
make the tests stop colliding. The two answers lead to different products:

| If sharing across processes **is** a product requirement | If it is **not** |
|---|---|
| Cross-process coordination is the fix, and the tests should prove it | The root derives from an isolation boundary — worktree, run, or session identity |
| A lock must not become stale or a false authority in its own right | The deliberately-shared cases opt into a dedicated shared root |

## Competing properties the remedy must hold at once

```text
must preserve:
  shared-cache semantics where the product requires them
  provenance case 9 — it is ABOUT a shared cache and must keep one
  identity re-verification
  repair-before-use
  refusal of unverified bytes
  deterministic concurrent execution

must avoid:
  global serialisation of the whole suite      -- hides the defect, and does nothing
                                                  for the cross-process case at all
  weakening assertions
  per-test isolation that makes shared-cache behaviour untestable
  a lock that can itself become stale or a false authority
```

**Do not carry the old symptom list forward as evidence** — it was produced against code that no
longer exists.
