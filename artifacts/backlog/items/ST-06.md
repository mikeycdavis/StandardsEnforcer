## What

Five configurations applied to a real GitHub repository, recorded before application and observed
after, with both preserved in `m4-raw/`.

## Why

M2's mitigation for the spoofable-check finding was an app binding. Nothing had ever tested it
against a real ruleset, and nothing in the documentation says it fails.

## Notes

It fails. A pull request emitted the required context name from a local job and GitHub returned
`{"name":"standards / machine-learning","app":15368,"conclusion":"success"}` with
`mergeStateStatus: CLEAN`.

Cases 1 and 1′ are the same live configuration read by the enforcer before and after the finding —
`COMPLIANT, authoritative: true` then `GATE_CONFIG_INVALID, boundToActions: true`. Nothing about
GitHub changed between them. That pair is the most useful thing in the evidence file, because it
shows the defect was in the model rather than in the platform.

**Stated limitation, agreed rather than smoothed over:** both repositories share an account owner.
This establishes separation from the governed pull request, not from the repository owner or from
organisation-level administrative control. `--require-organisation-root` is therefore intentionally
unvalidated.
