## What

`materialise()` in `scripts/identity.mjs` returns as soon as `.enforcer-complete` exists:

```js
if (existsSync(marker)) return { ok: true, dir: dest, cached: true, why: null };
```

It does not re-run `git rev-parse HEAD` against the cached tree. On a cache hit, the enforcer executes
whatever is at `<cacheRoot>/<sha>/` on the strength of a marker file saying that directory was once
verified. `DEFAULT_CACHE` is `path.join(tmpdir(), "standards-enforcer-cache")`.

## Why

**This is a false-green path in the identity model**, which is the one thing this repository exists to
prevent.

The whole point of the identity triple is that bytes verified are bytes executed. Step 3 of that model
— *the materialised checkout's HEAD is that commit* — runs once, at population time, and never again.
Cached verification is not permanent verification: a marker recording that an artifact was verified in
the past cannot substitute for evidence that the artifact about to be consumed is still that artifact.

The cache root is world-writable on most systems, and lives outside any repository, so nothing about
its contents is protected between runs. A cached entry is exactly the writable-surface case
`scripts/identity.mjs` opens by warning about at one remove: *"an artifact asserting the right thing is
not evidence that the thing is true."* The marker is such an artifact.

Note what this is **not**: it is not a claim that the cache is currently wrong anywhere, and no
exploitation has been observed. What is established is that the guarantee is not enforced on the
second and subsequent runs.

## Notes

**Found during the EngineeringStandards adoption on 2026-08-11**, by reading the identity model
against the governing constraint that a cache marker cannot stand in for current identity. It was not
found by a test, which is itself the finding: nothing exercises the cache-hit path adversarially.

**The falsifier is concrete and should be written before the fix** — the guarantee is "a cache entry
whose contents no longer match its name is refused", so:

> Populate the cache for a known SHA, let the marker be written, then modify the cached checkout —
> move HEAD, or alter a file the evaluator reads. Run again against the same identity. The run must
> refuse rather than execute the modified tree.

Write it, watch it fail against the current implementation, and only then change `materialise()`.
A guard that was never seen to bite is not evidence.

**Cost is worth stating, because it is the reason the shortcut exists.** Re-verification per run is one
`git rev-parse HEAD`, which is why the current behaviour is a shortcut rather than a design. Note that
`rev-parse HEAD` alone establishes the commit, not that the working tree matches it — deciding how far
to go (HEAD only, or a dirty-tree check) is part of the decision, not a detail.

**This reopened EP-01.** That epic was closed on 2026-08-10 claiming authority transport under a pinned
identity; this finding says the pinning has a hole on every run after the first. The evidence EP-01
cited is still true about what was established then — it is the completion claim that did not survive.
All of EP-01's enumerated children remain complete, which is precisely why a parent must not be
declared done merely because its listed children are.
