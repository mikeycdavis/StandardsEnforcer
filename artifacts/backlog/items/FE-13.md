## What

`materialise()` in `scripts/identity.mjs` returns as soon as `.enforcer-complete` exists:

```js
if (existsSync(marker)) return { ok: true, dir: dest, cached: true, why: null };
```

It does not re-run `git rev-parse HEAD` against the cached tree. On a cache hit, the enforcer executes
whatever is at `<cacheRoot>/<sha>/` on the strength of a marker file saying that directory was once
verified. `DEFAULT_CACHE` is `path.join(tmpdir(), "standards-enforcer-cache")`.

## Why

**This is a false-green path in the identity model**, which is the one thing this repository exists to
prevent.

The whole point of the identity triple is that bytes verified are bytes executed. Step 3 of that model
— *the materialised checkout's HEAD is that commit* — runs once, at population time, and never again.
Cached verification is not permanent verification: a marker recording that an artifact was verified in
the past cannot substitute for evidence that the artifact about to be consumed is still that artifact.

The cache root is world-writable on most systems, and lives outside any repository, so nothing about
its contents is protected between runs. A cached entry is exactly the writable-surface case
`scripts/identity.mjs` opens by warning about at one remove: *"an artifact asserting the right thing is
not evidence that the thing is true."* The marker is such an artifact.

Note what this is **not**: it is not a claim that the cache is currently wrong anywhere, and no
exploitation has been observed. What is established is that the guarantee is not enforced on the
second and subsequent runs.

## Notes

**Found during the EngineeringStandards adoption on 2026-08-11**, by reading the identity model
against the governing constraint that a cache marker cannot stand in for current identity. It was not
found by a test, which is itself the finding: nothing exercises the cache-hit path adversarially.

## Acceptance property

Decided 2026-08-11 and restated by the owner on 2026-08-12, deliberately stronger than "re-check
`HEAD` once more". The owner's wording governs:

> **Every execution must establish that the materialised authority's current identity still matches
> the authority identity that was resolved and approved for that run. Cached state may avoid
> reacquisition, but it may never substitute for identity verification.**

The earlier formulation said the same thing about the moment of consumption; this one is binding
because it names *the identity resolved and approved for that run* as the thing to match against, so a
cached tree that is internally consistent but belongs to some other run's authority does not satisfy
it. It also fixes caching's place: an optimisation that avoids reacquisition, never a component of
the trust model.

The wording matters. A fix that verifies once and then caches *the verification* satisfies the weaker
reading and reintroduces the same defect one level up — it would replace a marker asserting the tree
was verified with a variable asserting the same thing. Identity is established when the checkout is
used, or it is not established.

## Start from the red reproduction, not from a proposed fix

```text
materialise a valid pinned checkout
  → marker exists
  → alter/corrupt the cached checkout
  → invoke materialise again
  → current implementation accepts the cache hit      [expected red reproduction]
```

Freeze that reproduction before designing any remedy. A guard that was never seen to bite is not
evidence, and the point of writing it first is that the current implementation must be *observed*
failing rather than assumed to fail.

At least three cases should be covered, because they fail differently:

1. **Wrong `HEAD`** — the cached tree is a real checkout of a different commit.
2. **Missing or corrupt marker metadata** — the marker is absent, empty, truncated, or names a
   different SHA than the directory it sits in.
3. **A directory that exists but no longer proves the requested identity** — the general case, and the
   one the first two are instances of. The cache entry is present and superficially well-formed, and
   nothing about it establishes *(repository, tag, SHA)*.

**The mechanism follows the evidence.** Do not pick between re-verification, revalidation on read, or
abandoning the cache until the reproduction shows which failures are real.

**Cost is worth stating, because it is the reason the shortcut exists.** Re-verification per run is one
`git rev-parse HEAD`, which is why the current behaviour is a shortcut rather than a design. Note that
`rev-parse HEAD` alone establishes the commit, not that the working tree matches it — deciding how far
to go (HEAD only, or a dirty-tree check) is part of the decision, not a detail.

**This reopened EP-01.** That epic was closed on 2026-08-10 claiming authority transport under a pinned
identity; this finding says the pinning has a hole on every run after the first. The evidence EP-01
cited is still true about what was established then — it is the completion claim that did not survive.
All of EP-01's enumerated children remain complete, which is precisely why a parent must not be
declared done merely because its listed children are.

## Closed 2026-08-12

Shipped in `0.4.1`. Full account in
[`2026-08-12-fe13-cache-identity.md`](../../evidence/2026-08-12-fe13-cache-identity.md); what matters
here is what the reproduction decided, since the item deliberately left the mechanism open.

**The red was observed, not assumed** — four of six cases failed against the unfixed implementation,
and the raw output is frozen in `2026-08-12-fe13-cache-identity-raw/red-before.txt`.

**The two marker-metadata cases passed, and that chose the remedy.** The marker's content was never
read, so corrupting it changed nothing. Making the marker load-bearing — the fix this item's title
invites — would have replaced a marker asserting the tree was verified with a marker asserting it more
carefully. The tree is the evidence; the marker is bookkeeping. Both cases were kept anyway, because
the property must hold whatever the marker says.

**HEAD-only versus dirty-tree was decided by the evidence, as the item required.** The edited-`VERSION`
case kept a correct `HEAD` and executed different bytes, so the check is `HEAD` *and* a clean tree —
which is why the completion marker moved out of the checkout rather than being excepted from it.

Two things surfaced during the work, both recorded in the evidence and neither cosmetic:

- A real MachineLearningStandards cache entry on this machine was **five files short**, and the old
  implementation had been executing it. The defect was biting outside its own fixture.
- The first fix deleted rejected entries in place, which raced with concurrent runs and threw
  `ENOTEMPTY` out of `materialise`. An exception is a third outcome this module does not have. Repair
  now stages and renames, and filesystem faults return a reason.

**Deliberately still open, and not tracked as items:** verification happens at materialisation rather
than continuously, and concurrent repair has no cross-process lock. Both are stated in the evidence
and in `CHANGELOG.md`. Neither has been forced by anything; a lock added now would be a mechanism
built ahead of its case.

**EP-01's disposition is not decided here.** This item owned the gap that reopened it, and the gap is
discharged — but that parent was reopened on a judgement about a broader claim, and re-closing it is
the same kind of judgement. It stays `IN_PROGRESS` with every child complete until its owner says
otherwise, which is the state `backlog-reconcile` is designed to surface rather than a defect in it.
