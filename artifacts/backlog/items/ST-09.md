## What

`scripts/ci.sh` cannot build the CI image under Git Bash on Windows. MSYS rewrites the staged
build-context path on the way to Docker, and the build fails:

```text
unable to prepare context: path "F:\Repos\StandardsEnforcer-localci\tmp\
localci-stage-localci-standardsenforcerlocalci-bf186e29f44d-70790" not found
```

Reproduced on `main` at `bf186e2` immediately after the merge, running `bash scripts/ci.sh` from
the repository root.

## Why

`scripts/ci.ps1` works and is the Windows entry point, so nobody is blocked from authoritative CI
and this is **not an integrity defect**: the failure is loud, occurs at build time, and cannot
produce a passing result. It is a portability and usability defect — the documented POSIX-style
entry point does not work on the platform this repository is actually developed on.

What makes it earned rather than noticed: `87f543b` fixed **this same class of defect** in
`scripts/submit-pr.sh`, where MSYS rewrote the container paths passed to `ci/verify.mjs`. The
mechanism is understood and the remedy exists one file over. Leaving the sibling unfixed is an
inconsistency, not an unknown.

That commit also records why the class matters more than it looks: a guard that fails for the wrong
reason still stops the push, so it looks safe and is not — the operator is told the verification
refused when in fact it never ran. The `ci.sh` instance does not have that property, which is why
this is filed at lower priority than [ST-08](./ST-08.md).

## Notes

Acceptance criteria, deliberately narrow:

- reproduce under Git Bash on Windows;
- fix the staged-context path handling **without changing `ci.ps1` semantics**;
- prove `ci.sh` and `ci.ps1` still drive the same authoritative pipeline;
- run both the success and the failure path;
- preserve the `git archive` commit-source invariant — the staged context must remain the exact
  committed tree, and no working-tree state may become reachable as a side effect of the fix;
- **no new alternate orchestration logic in the shell script.** A second code path that only Windows
  takes would mean the two entry points no longer verify the same thing, which costs more than the
  bug does.

**Parentage, and its weakest point.** [EP-06](./EP-06.md) owns this repository's own authoritative
assurance surfaces, and `scripts/ci.sh` is one of the two entry points to that surface. On the
platform this repository is developed on, only one of the two works.

The honest caveat: EP-06's stated property is that a surface must *establish what it reports*, and
this defect does not touch that — `ci.sh` reports nothing false, it fails. If EP-06 is read strictly
as being about claims rather than about the surfaces that produce them, this item wants a different
home. EP-04 was the alternative considered and rejected: its subject is release *identity*
(`VERSION`, `package.json`, `SCHEMA_VERSION`), not tooling. Filed here rather than held, because a
reproduced defect should be recorded before its taxonomy is settled — and re-parenting is one line.
