## What

`scripts/ci.sh` and `scripts/ci.ps1` are both documented as ways to run authoritative CI. This
feature owns the property that both of them **work**, on the platforms they are offered on, and that
they drive the same pipeline rather than two pipelines that happen to share a name.

## Why

[ST-09](ST-09.md) is the live instance: `scripts/ci.sh` cannot build the CI image under Git Bash on
Windows, because MSYS rewrites the staged build-context path on the way to Docker.

```text
unable to prepare context: path "F:\Repos\StandardsEnforcer-localci\tmp\
localci-stage-localci-standardsenforcerlocalci-bf186e29f44d-70790" not found
```

**This is deliberately not an integrity defect, and that is why it is here rather than under
[EP-06](EP-06.md).** ST-09 draws the line itself: *"the failure is loud, occurs at build time, and
cannot produce a passing result … It is a portability and usability defect — the documented
POSIX-style entry point does not work on the platform this repository is actually developed on."*

**Earned rather than noticed.** `87f543b` fixed the same class of defect in `scripts/submit-pr.sh`,
where MSYS rewrote the container paths passed to `ci/verify.mjs`. The mechanism is understood and
the remedy exists one file over; leaving the sibling unfixed is an inconsistency, not an unknown.

That commit also records why the class matters more than it looks — a guard that fails for the wrong
reason still stops the push, so it looks safe and is not. **The `ci.sh` instance does not have that
property**, and the distinction is load-bearing for where this feature sits: a variant that *did*
have it would belong to EP-06, not here.

## Acceptance

ST-09's criteria, deliberately narrow, and unchanged by the reparenting:

- reproduce under Git Bash on Windows;
- fix the staged-context path handling **without changing `ci.ps1` semantics**;
- prove `ci.sh` and `ci.ps1` still drive the same authoritative pipeline;
- run both the success and the failure path;
- preserve the `git archive` commit-source invariant — the staged context must remain the exact
  committed tree, and no working-tree state may become reachable as a side effect of the fix;
- **no new alternate orchestration logic in the shell script.** A second code path that only Windows
  takes would mean the two entry points no longer verify the same thing, which costs more than the
  bug does.

## Scope

One property, two scripts. This feature is **not** a general portability programme and does not
adopt one: ST-09's own rule applies to its parent as well as to itself — a remedy is earned by a
defect, not by a category. Nothing here bears on [EP-05](EP-05.md)'s reach, where *platform* means a
second forge rather than a second shell.
