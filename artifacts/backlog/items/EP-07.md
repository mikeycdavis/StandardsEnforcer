## What

The build and verification machinery itself: the entry points that stage a commit and start the
authoritative pipeline, and the composition of the suite that pipeline runs. This epic owns whether
that machinery **works on the platforms it claims, and runs what it says it runs**.

## Why

[EP-06](EP-06.md) owns whether a green result is true. That question only arises for a run that
happened. Two defects recorded on 2026-08-16 and 2026-08-23 are one step earlier than EP-06's
property and were filed with no epic that fits them:

- [ST-09](ST-09.md) — `scripts/ci.sh` cannot build the CI image under Git Bash on Windows. It fails
  loudly at build time and certifies nothing, which is precisely why EP-06 is the wrong owner: *"It
  does not certify something it failed to establish"* (ST-09's own rejection table).
- [ST-13](ST-13.md) — `npm test` was `node --test` with no operand, so a hosted run recursively
  discovered `.oracle/test/**` and executed MachineLearningStandards' suite alongside this one.

Neither is about a claim being false. Both are about the pipeline's *composition* — which script can
start it, and which files it consists of.

## Why not an existing epic

Created 2026-09-18 by owner disposition, after checking all six existing epics against ST-09 rather
than assuming none fit. ST-09 had already published four of these rows and declined to invent an
epic for one specimen; the fifth and sixth rows are added here.

| Epic | Its property | Why not |
| --- | --- | --- |
| EP-01 | authority transport under a pinned identity | Wrong axis entirely. Nothing here touches a pack, a release identity or an evaluator |
| EP-02 | whether a governed pull request can satisfy its own enforcement root | Unrelated — ST-09's row, unchanged |
| EP-03 | every repository has an explicit scope disposition | Unrelated, and COMPLETE since 2026-08-09 |
| EP-04 | this repository's own release identity — `VERSION`, `package.json`, `SCHEMA_VERSION` | Strictly versioning, not tooling — ST-09's row, unchanged |
| EP-05 | reach beyond one repository, one platform, one standard | *"'Platform' there means a second forge, not a second shell or OS"* — ST-09's row, unchanged. EP-05's `What` is the README's own gap list, which names none of this |
| EP-06 | this repository's assurance claims must establish what they report | The closest fit and still wrong for ST-09, per its own scope note forbidding a catch-all merely because a test is involved |

**The threshold ST-09 set has been met.** It declined an epic on the grounds that *"One loud shell
bug is not evidence for a local-tooling epic; the next independently earned defect of the same kind
would be."* ST-13 is that defect — independently earned, found while closing [FE-14](FE-14.md),
about the same machinery and not about a false claim. Two, not one, is what makes this epic
narrower than a catch-all.

## Scope boundary

This epic owns **the pipeline's ability to run, and its composition**. It does not own whether a run
that completed reported truthfully — that stays with EP-06, and a finding must not arrive here
merely because CI was involved. The test for which side a finding falls on is the one ST-09 used:
did the machinery fail loudly, or did it certify something it had not established?

**Moving [ST-13](ST-13.md) here is a disposition, not a correction.** ST-13's own text argues it is
EP-06's problem — *"an assurance surface reporting more than it establishes, which is this epic's
property exactly"* — and that argument is not withdrawn. The owner's reading is that its outcome is
the composition of the suite, which is this epic's, and both readings are on the record.
