## What

[ST-11](ST-11.md) found one source-scanning test that became vacuous because the bytes it read were
not the bytes it was written against. This item asks the question ST-11 deliberately did not answer:
**is that one specimen, or a class?**

## The established fact, stated no wider than it was measured

> Authoritative CI may execute text whose line endings differ from the committed blob, and at least
> one source-inspection test was line-ending-sensitive enough to become vacuously green.

That is all. Specifically **not** established:

- that `.mjs` must be pinned to `text eol=lf`;
- that any other scanner is affected;
- that the line endings are a defect at all. Node does not care, and `.gitattributes` already pins
  `*.sh` for a reason that was real and named (a CRLF shebang is unparseable inside the container).

## Why the obvious remedy is not adopted yet

Pinning `*.mjs text eol=lf` repository-wide would have prevented ST-11's instance, which makes it
tempting. It is being held because it solves the scanners' *environment* rather than the scanners:
a normalised tree makes a fragile extraction work again without making it report when it stops
working. ST-11's repair — assert the extraction found something — survives a future environment that
normalisation does not anticipate. A tree-wide `.gitattributes` change also rewrites every `.mjs` in
every working copy, which is a large diff to take on evidence of one.

If the audit finds several affected scanners, a repository-level text invariant becomes earned and
can be argued on its own evidence. If ST-11 is the only one, fixing the scanner was the right
boundary and this item closes with that finding recorded.

## How

Enumerate every test that reads source (or any repository file) **as text** and derives structure
from it — `readFile` plus `indexOf`/`slice`/`split`/`match` over the result. `test/authority-boundary.test.mjs`
is the known starting point: it scans `scripts/**/*.mjs` for ADR 0001's prohibited domain vocabulary,
it is one of the oldest guards here, and it is the one whose silence would matter most.

Classify each into exactly one of:

```text
1. line-ending agnostic already          → no action
2. sensitive, but fails loudly           → no action; record why it is loud
3. sensitive, and can succeed vacuously  → a live assurance defect
```

Only class 3 is a defect. For each class-3 finding, the ST-11 pattern is the remedy: normalise,
locate, **assert located**, assert the region is the intended one, then assert.

A scanner should be classified by *execution*, not by reading it — feed it CRLF input and observe.
Reading ST-11's guard did not reveal the defect; running it against archived bytes did.

## Acceptance

- Every source-reading test in the suite is enumerated and classified, with the classification
  method recorded per test rather than asserted.
- Every class-3 finding is either repaired to the ST-11 pattern or has a recorded reason it is not.
- The `.gitattributes` question is answered **from the resulting count**, in either direction, and
  the answer is written down with its evidence — including the answer "no change".
- No scanner is repaired by rewording the source it scans.

## Closure

Closed 2026-08-26. The question this item asked — **one specimen, or a class?** — is answered:
**one specimen.** Zero further class-3 findings.

The audit and its method are in
[artifacts/evidence/2026-08-26-source-scan-audit.md](../../evidence/2026-08-26-source-scan-audit.md).
In summary, against the 29-file surface `scripts/test-surface.mjs` enumerates:

```
reading any path as text          14
  classified by execution         12
  excluded, reason recorded        2   identity-cache reads a temp checkout it wrote;
                                       policy-path performs no read at all
class 1  agnostic                 11
class 2  sensitive, fails loudly    1   checkout-line-endings
class 3  vacuously green            0
```

> **The 29-file denominator is historical-at-execution.** It is the surface at `721a97b`, which is
> what ran. At `6587b23` the surface had reached **32** files, and at `bd23a32` it is **34**. All three additions have since been classified
> by execution rather than assumed: `test/adoption-marker.test.mjs` reads no repository source and
> joins the excluded category, while `test/diagram-sync.test.mjs` and
> `test/identity-before-adoption.test.mjs` both do read source and both went red under mutation on a
> CRLF tree — class 1. **Zero class-3 therefore holds for the current surface, not only the
> historical one.** See the note in the evidence file; the original count is not re-derived, because
> a denominator edited to match today stops being evidence of what was executed.

Classification was by **execution**, as this item required: a CRLF scratch tree built from
`git archive HEAD` — 169 converted files, the same 169 `d07b73b` named — and then, for each test,
the specific defect it exists to catch planted in that tree. Passing under CRLF proves nothing on
its own, because passing is precisely what a vacuous scanner does; going red with the defect
present is what establishes the guard is live.

The harness asserts its own mutation landed. A no-op edit produces a green run that reads as a
vacuous guard, and that happened once here, producing a false class-3 verdict against
`test-support/source-scan.mjs` which was withdrawn on inspection. Failing closed on a no-op is the
same INV-E1 shape this repository applies everywhere else.

**No repair was made, because nothing was vacuous.** Acceptance criterion 2 is satisfied by an
empty set rather than by a fix.

**Acceptance criterion 3 — the `.gitattributes` question — is satisfied by provenance, not by this
audit.** `* text=auto eol=lf` landed in `2b88466` (#21, 2026-08-18, claimed by EP-04), two days
after this item was opened, which is why the text above still describes the pin as being held. That
decision is not reopened here, and the count does not bear on it: the pin exists because a checkout
should not be a property of the machine, which is true whatever the scanners do. What the count
*does* settle is the narrower question this item owned — **fixing the scanner was the right
boundary**, and [ST-11](ST-11.md) drew it in the right place.

One observation recorded and deliberately not repaired: `test/enforce.test.mjs` duplicates the
comment-stripping logic instead of using `test-support/source-scan.mjs`, and carries no liveness
assertion. It is class 1, and it cannot scan nothing — it names three files and `readFile` throws
on a missing path — so it is sound for a structural reason rather than a deliberate one. Adopting
the shared helper there is a separate decision with its own evidence, not a repair this item was
entitled to make.

**EP-06 is not closed by this.** After this item closes the epic still retains an open child,
[ST-14](ST-14.md) — but that is not the reason, and the reason would be unchanged if it were the
last: a parent closing is a guarantee-level decision about whether the epic's property holds, not an
arithmetic consequence of its enumerated children being done. That decision is left open
deliberately.
