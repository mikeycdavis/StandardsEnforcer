## What

`scripts/scope.mjs` reads a hardcoded `entry.machineLearning` key from the registry, and names
MachineLearningStandards in its own prose when a repository is unreviewed. There is no way to record
a disposition for any other pack.

The applicability unit should be *repository × standards pack*. Today one pack is privileged in code,
so a repository that is in scope for Engineering and out of scope for Betting cannot be expressed at
all — and neither can any disposition for the pack this repository has just adopted.

## Why

Found during the EngineeringStandards adoption on 2026-08-11, and it is what forced that adoption's
`IN_SCOPE` record to be held in evidence rather than in the registry the enforcer reads. The
disposition is a real, decided fact that the enforcement path has nowhere to put.

The registry *format* is already pack-shaped — `repositories.<id>.machineLearning` — so the data model
anticipated this. Only the reader did not.

## Notes

**Not scheduled, and deliberately not designed here.** Recorded because the adoption produced evidence
that something should change, which is the bar for an item at all. The mechanism is a decision that
has not been taken.

Two things a future implementer should know before starting:

- The registry key would become the pack's `standard.id` from its `standards-adapter.json`
  (`machine-learning`, `engineering`, …), which is the identifier the pack itself owns. Migrating
  existing `machineLearning` entries is a compatibility question, not just a rename.
- `scripts/footprint.mjs` detects **ML** evidence specifically. Making scope multi-pack does not make
  detection multi-pack, and it must not appear to: detection is evidence and decides nothing
  ([ADR 0004](../../adr/0004-scope-is-a-recorded-decision.md)). A pack with no detector is not a pack
  whose detector found nothing.

## Acceptance condition, and its falsifier

The guarantee this item would establish:

> A repository can carry an independent, simultaneous scope disposition for each standards pack, and
> no pack is privileged by the enforcer's code.

**The falsifier, to be written first and watched fail against the current implementation:**

> Build a registry entry recording one repository as `in-scope` for one pack and `out-of-scope` for a
> second, each with its own reviewer, date, reason and evidence basis. Resolve scope for both packs.
> Each must return its own disposition. Against `scope.mjs` today this cannot even be expressed: the
> second pack's disposition is unreadable, because only `entry.machineLearning` is consulted.

A second, cheaper falsifier guards the leak rather than the feature, and should outlive it:

> Assert that no executable source under `scripts/` names any specific pack. `machine-learning`,
> `machineLearning` and `MachineLearningStandards` currently appear in `scripts/scope.mjs`. This is
> the same shape as the existing guard in `test/authority-boundary.test.mjs`, which already asserts
> that the enforcer holds no pack's verdict vocabulary — the scope layer simply was never covered by
> it.

**Done is not "it works for engineering".** Done is that adding a pack requires no change here at all.
If the implementation ends up with a list of known pack ids, the abstraction has not been built.

## Closed 2026-08-12

Shipped in `0.5.0`. Full account in
[`2026-08-12-fe12-multi-pack-scope.md`](../../evidence/2026-08-12-fe12-multi-pack-scope.md).

**Both falsifiers were written first and observed red**, and the cheap one was the more informative.
`test/authority-boundary.test.mjs` had banned pack identity in `scripts/` since M2 and had been
passing the whole time, because its list held the contract id `machine-learning` while `scope.mjs`
wrote `machineLearning`. One pack was privileged in code for the whole of M3, two files from a test
asserting that could not happen. The guard now covers the non-canonical spellings.

**The mechanism decision the item left open**, and the one place the first attempt was wrong: the
asking pack's id comes from the **invocation** (`--standard`), not from `standard.id` in the pinned
release's adapter. Reading it from the contract looks stricter and failed seven tests in
`scope-seam-invariance.test.mjs`, including *"a reviewed exclusion survives a malformed adapter"*. A
human decided the standard does not govern the repository; a broken contract is not new information
about that decision. Scope authority sits outside the evaluator seam, and the stricter-looking design
would have moved it inside.

**No legacy key is accepted.** Reading `machineLearning` would require the enforcer to know one pack's
name. An unmigrated registry is `SCOPE_REVIEW_REQUIRED` — fail-safe and visible. Migration is a
registry edit.

**Detection was not generalised, and the item was right to warn about it.** One detector, one surface,
now named in the basis (`training-evidence` — named for the evidence, not for a pack). A basis naming
a surface a run did not observe is *undetermined*, not stale and not fresh.

Three things this did **not** do, all in the evidence: the EngineeringStandards `IN_SCOPE` decision is
still unmigrated (this removes the obstacle; recording it is a reviewer's act, not a code change), no
other pack gained a detector, and `--standard` is unvalidated beyond presence — a typo and a genuinely
unreviewed pack look the same from the outcome alone.
