## What

Two suites consume the oracle in two different senses, and only one of them is identity-bound.

**The authority half is object-addressed, and was audited rather than assumed.** The complete chain,
measured at `2ba90ac`:

```text
ENFORCER_ORACLE_REPO                 a host path — mutable, and a transport only
  git rev-list -n 1 <tag>            test-support/oracle.mjs, scripts/identity.mjs:87
  verifyTagResolvesTo(repo,tag,sha)  the declared SHA or nothing runs
  git clone --no-checkout            scripts/identity.mjs:427 — from the object database
  git checkout --detach <sha>        scripts/identity.mjs:432
  checkoutIsExactly(dir, sha)        :258 — HEAD == sha, tracked tree matches, ignored content reviewed
  loadAdapter(id.dir)                enforce.mjs:134 — contract read under the verified checkout
  spawn(execPath, [entrypoint])      :323 — entrypoint realpath-contained in that checkout
```

No byte of the oracle's working tree reaches the executed evaluator. A cache hit is re-verified
before reuse rather than trusted (`:409`). This half satisfies the property.

**The subject half is not.** `test/enforce.test.mjs` hands the oracle's *working tree root* in as the
governed repository:

```js
:209  const r = await enforce({ ...identity(), target: MLS });
      assert.equal(r.authority.status, "NOT_EVALUATED");

:225  const direct = runOfficialEvaluator(id.dir, { target: MLS, policyPath: path.join(MLS, "project-policy.yml") });
:226  const viaEnforcer = await enforce({ ...identity(), target: MLS });
```

`MLS` is `ORACLE_REPO` — the host checkout, at whatever state it happens to be in. The evaluator
reads that tree from disk: `MachineLearningStandards/scripts/standards.mjs:694` selects
`f.ext === ".md" && f.text`, and its git fast path at `:183-195` uses git for **filenames only**,
reading bytes back off disk. A git invocation that looks object-addressed and yields working-tree
bytes is the sharper form of this finding.

## Why this is EP-06's problem

Not hypothetical. During the audit of 2026-08-16 the oracle host tree was observed moving from a
dirty `27d4b61` to a clean `7826f24` **while CI had it mounted**. `read_only: true` on the bind
establishes that the container cannot write the oracle; it establishes nothing about the host
writing it concurrently. Those are different integrity directions and only the first is covered.

Two failure directions, both live:

- **Content-dependent verdict.** `:209` asserts `NOT_EVALUATED`, which arises from the oracle's
  `project-policy.yml` and the markdown its evaluator reads. A concurrent edit to either is exactly
  the class of change that feeds that assertion.
- **Time-dependent comparison.** `:225-226` compares two runs against the same path. The assertion
  is content-invariant but not time-invariant: a tree that changes *between* the two runs produces a
  field-level difference with no local cause.

The acceptance property this fails:

> Oracle-dependent evidence must identify immutable Git objects whose bytes are the bytes consumed.
> A mutable host working tree may be a transport for the object database, but must not itself be
> the authority.

## Acceptance

1. Every oracle-dependent assertion states which bytes it consumed, for the **subject** as well as
   the authority.
2. Where the subject is the oracle repository, it is materialised at a named commit by the same
   verified route the authority already uses — not read from `ORACLE_REPO` in place.
3. A regression test establishes the exclusion: no oracle-dependent assertion **that consumes the
   subject's bytes** may take `ORACLE_REPO` as a target path directly. Asserting today's verdict is
   not that test.

   > **Amended 2026-08-27 — narrowed to content-consuming assertions.** It read: *"no
   > oracle-dependent assertion may take `ORACLE_REPO` as a target path directly."* Read as text,
   > that swept in `enforce.test.mjs`'s identity-mismatch case, which passes the oracle as `target`
   > under a SHA that cannot resolve. Settled by execution rather than by grepping for `target:`:
   > that call answers identically over the oracle checkout and over an empty directory — two
   > targets sharing no content — in state, in the absence of a report, and in the message. An
   > answer that is the same for two disjoint inputs is not a function of either one's bytes, so
   > rewriting that call would have been an edit made to satisfy the shape of a sentence. The
   > narrowing follows this item's own body, which never listed that site: the three it names are
   > `:209`, `:225` and `:226`, all of which do consume the subject. The boundary is asserted, not
   > asserted-about, by `boundary · an identity mismatch consumes no subject bytes at all`.
4. The recorded evidence names repository, tag and **peeled commit SHA** for both halves. A SHA
   appearing somewhere in the output does not satisfy this.
5. The oracle integration still executes. A remedy that narrows the surface until the
   oracle-dependent tests fall outside it is the [FE-14](FE-14.md) defect returning by another
   route, and is refused here as it is there.

## Closure — 2026-08-27

Closed on evidence, in two parts, because the first remedy satisfied the item's text while leaving
its property unestablished.

**The subject is materialised through the authority's own verified route.** `test-support/oracle.mjs`
gained `oracleSubject(hostRepo, sha, cacheRoot)`, which calls the same `materialise` the authority
goes through: clone from the object database, `checkout --detach` onto the SHA, then
`checkoutIsExactly` before the directory is returned. One mechanism, one set of guarantees. A bespoke
copy would be a second definition of *"these bytes are that commit"*, free to drift from the first;
copying the working tree would fix the bytes for the run but pin them to no identity. Materialisation
failure returns `ok: false` with a reason and no directory — there is no fallback to the host, which
would restore the defect behind a helper reporting success.

**The subject and the authority do not share a cache entry, and that is load-bearing.** The first
remedy on this line resolved both roles through one `cacheRoot`. `materialise` keys an entry by SHA
alone, and here the subject's commit **is** the authority's commit — an oracle evaluated under its
own release is the point of these tests — so both roles received one directory. Measured on that
design:

```text
subject dir == authority cache entry     true
mutate the subject, then enforce         applicable 0 -> 0      (unchanged)
mutation surviving on disk afterwards    false                  (repaired)
```

The authority's own verification found the subject's state and repaired it before any assertion could
observe it. Every prohibition still passed; what could not be established was that the subject was
read at all. `oracleSubject` namespaces the subject beneath `<cacheRoot>/subject`, and the liveness
falsifier below fails on the shared design and passes on the namespaced one.

**A source scan cannot see this.** The scan added with the first remedy is retained — it is a real
guard, it derives its aliases rather than listing them, and it strips comments so a suite may explain
itself without the explanation being the violation. But it reports that nobody *wrote* the defect; it
cannot report that the subject is frozen when the code *runs*. The behavioural falsifiers are what
distinguish "the subject is frozen" from "the subject is never read", and they are why this item
closes rather than merely passing.

| Falsifier | Shared cache | Separate cache |
| --- | --- | --- |
| the mutation is observable in the report at all | pass | pass |
| editing the host checkout does not change what was evaluated | pass | pass |
| the identity is established from the checkout, not assumed | pass | pass |
| mutating the frozen subject **does** change the result | **fail** | pass |
| an unmaterialisable identity fails, never falls back to the host | **fail** | pass |
| an identity mismatch consumes no subject bytes at all | pass | pass |

Rows 1, 2 and 6 pass in both columns by design. They are what stops the others from going green
vacuously.

**Both halves are named.** Authority and subject are each `MachineLearningStandards`, tag `v1.6.0`,
peeled commit `eda15a2f56299bc0acc29feb5516dd7c6b8e475d` — peeled with `git rev-list -n 1 <tag>`,
which dereferences an annotated tag to its commit. That they coincide is what made the defect
invisible and what broke the first remedy.

**EP-06 is not closed by this.** Its enumerated children now compute 7/7, and that is not the
question. Whether the epic's guarantee holds is a decision about the property, not an arithmetic
consequence of its children being done, and it is left open deliberately.

## What this item does not do

**It does not block FE-16, and must not be read as doing so.** That expectation was carried into
this audit and the measurement contradicts it. FE-16's replay harness
(`artifacts/evidence/2026-08-16-fe16-red-replay.harness.mjs`, at `44027b2`) builds synthetic packs
and a synthetic governed target under `mkdtemp` and touches the oracle **not at all** — its subject
is immutable by construction for the length of the run. Naming FE-16 as blocked by this item would
manufacture a dependency the code does not have, which is the same shape of unearned claim this
epic exists to remove. FE-16 remains unfinished for its own reasons: no signal check and no
declared-passing-versus-nonzero-exit contradiction check exists in `scripts/enforce.mjs` at
`2ba90ac`, and FE-16 has no item file on this line at all.

**It does not restate [ST-13](ST-13.md).** ST-13 is about which *tests* the runner discovers when
the oracle is checked out beneath the root. This is about which *bytes* an oracle-dependent test
consumes once it runs. A repository could fix either and still hold the other.

**It does not convert the observed `PROJECT.md` edit into a defect claim.** That edit is external
state and is useful evidence exactly as observed. What is filed here is that mutable working-tree
edits *can* reach the result, established from the consumption path — not that this particular one
did.
