> **Closed 2026-08-13 with one arm platform-pending.** Cases 1–4 are proven; case 5's universal
> property is proven and its `null`-specific **reason** has never executed, because Windows cannot
> produce a process with no exit code. It runs for real on the next Linux CI execution. See
> [the evidence](../../evidence/2026-08-13-d3-exit-contradiction.md); no null status was faked
> locally to make the branch look exercised.

## What

`scripts/enforce.mjs` derives the whole of its verdict opinion from the pack's declared status:

```js
const passing = run.contract.result.passing.includes(status);
```

`run.exitCode` is carried into the payload as `standardsExitCode` and **never consulted**. So a pack
that declares a passing status and then fails to complete successfully — a nonzero exit, or no exit
code at all — is reported as `EVALUATED`, `passing: true`, and the enforcer exits `0`.

## Why

**This is INV-E1 violated in the one place it matters most.** The invariant says never convert an
unknown, missing, unverifiable or failed enforcement condition into a successful compliance result.
A declared pass alongside a failed process is not a verdict — it is authority evidence that
contradicts itself, and contradictory evidence is an unknown.

The concrete case is real and already shipped in the family:
`EngineeringStandards/scripts/standards.mjs` exits `EXIT_FINDINGS` when
`report.unestablishedProhibitions` is non-empty, while the report it printed can still carry a
passing status. That repository would pass this enforcer's gate.

## The claim is narrow, and it is not about exit codes

**StandardsEnforcer does not learn what a native exit code means, and must not after this closes.**
[ADR 0001](../../adr/0001-orchestrate-do-not-reimplement.md) forbids it and
[`states.mjs`](../../../scripts/states.mjs) records why there is nothing to learn: Betting exits `2`
on `NOT_EVALUATED`, MachineLearning `3` on blocked, Health `4`, Financial folds blocked into `1`.
There is no common meaning to read.

> **The property: a pack cannot be reported as passing when its process did not successfully
> complete.**

A **non-passing** native status with exit `2`, `4`, `17` or anything else remains entirely the pack's
business unless its own contract says otherwise. The enforcer is noticing exactly one impossible
combination — *"this passed"* alongside *"the process did not complete successfully"* — and nothing
wider. This is the residue the reconciliation adjudicated as **C-D**, and it is deliberately much
smaller than the superseded plan's D3, which proposed reading exit codes generally and was **rejected
on evidence**.

## Acceptance cases — frozen at `670d617`, before any remedy

```text
1  declared passing  && exitCode === 0     ordinary success           → EVALUATED, exit 0
2  declared failing  && exitCode !== 0     ordinary failure           → EVALUATED, exit 1
3  declared passing  && exitCode !== 0     contradictory evidence     → ENFORCEMENT_ERROR
4  undeclared status && exitCode !== 0     vocabulary error, FIRST    → ENFORCEMENT_ERROR
5  declared passing  && exitCode === null  completion not established → ENFORCEMENT_ERROR
```

**Cases 3 and 5 are the defect. Cases 1, 2 and 4 are controls**, the same discipline as
[FE-15](FE-15.md)'s falsifier: they pin guarantees the product already has, so a remedy cannot buy
case 3 by giving them up.

**Case 2 is the control that matters most.** A pack saying no and exiting nonzero is the commonest
real outcome in the portfolio. A remedy that turned it into an enforcement error would have made the
enforcer an exit-code interpreter — precisely what the superseded D3 was rejected for proposing.

**Case 4 is the control that proves the ordering.** Both conditions hold at once — the status is
undeclared *and* the exit code disagrees — and the vocabulary check must still win. `passing` is not
computable from a status the pack's contract never declared, so *"the status contradicts the exit
code"* is not a statement that run is in a position to make. The pack's native vocabulary keeps
first say over its own result.

**No case may depend on which nonzero code was returned.** Case 3's fixture uses exit `7` so that a
remedy special-casing `1` cannot pass it.

## Required implementation order

Cases 3 and 5 are both caught by `exitCode !== 0`, and collapsing them would be the smaller diff.
They are **different findings** — 3 is evidence that contradicts itself, 5 is evidence that is
missing — and both must remain distinguishable to a reader. Handle `null` explicitly, then nonzero
explicitly. The code should communicate the authority model rather than merely produce the correct
boolean.

```text
1. validate the native status is declared by the pack's contract
2. derive whether that declared status is passing
3. if passing:
     a. exitCode === null  → ENFORCEMENT_ERROR — process completion not established
     b. exitCode !== 0     → ENFORCEMENT_ERROR — passing status contradicts the process result
4. otherwise preserve existing non-passing handling unchanged
```

Step 1 must stay ahead of step 3; that is what case 4 asserts.

## Case 5 is platform-conditional, and says so rather than skipping

Windows has no signals — `process.kill` becomes `TerminateProcess`, which supplies an exit code — so
a killed evaluator arrives locally as case 3 and `status` is never `null`. Probed against the same
construct the fixture uses, not inferred from `process.platform`, and the probe fails loudly if the
fixture rather than the platform is at fault.

The universal property is asserted on **every** platform: *a killed evaluator must never produce a
passing enforcement result.* Only the assertion distinguishing the two **reasons** is guarded.

> **Do not fake a null process status locally to make the branch appear fully exercised.** The
> distinct no-exit-code reason is specified and tested but **platform-pending until Linux
> execution**. CI runs on `ubuntu-latest`, where it is observed for real.

Until then this item's own evidence must say so, on the same principle as [FE-14](FE-14.md): a proof
that has not executed is not a proof.
