> **Subject broadened 2026-08-13.** This item previously asked only about `m3-scope-registry`. An
> evidence sweep found a **third** unmerged line, `reconciliation/m3-corrected`, which nothing
> tracked. Broadened rather than answered by a second, competing branch-disposition item: two items
> each holding part of a topology decision is how a repository ends up with two answers about which
> branch is authoritative, which is the failure this item exists to prevent.

## What

Four lines are live and none is established as authoritative. `main` is behind all of them.

```text
main                            the default branch; the earliest answer
enforcement                     carries the M2 supersession evidence (M4 live findings)
m3-scope-registry               the breaking 0.4.0 release, M2 close, conformance boundary,
                                adapter provenance, M4 live-GitHub evidence. Pushed.
reconciliation/m3-corrected     3 commits not on the integration line — 3ac4431, b61841f,
                                2a2a4fe. A concurrently produced reconciliation.
reconciliation/m3-integration   this line: the reconciled plan, Phase 0, and the adjudication
```

Decide what `main` should say, and what happens to each of the other three.

## Why

`main` describes a repository at `0.2.0`/`0.3.0` version ambiguity with M2 open, while the working
lines describe `0.4.x`–`0.5.0` with M2 closed as `IMPLEMENTED — PORTFOLIO_BLOCKED` and Phase 0
hardening complete. Anyone reading the default branch gets the earliest answer.

**Two reconciliation lines is the newer and sharper problem.** `reconciliation/m3-corrected` and
`reconciliation/m3-integration` were both produced to reconcile the same divergence. Two branches
whose stated purpose is to *be* the reconciliation is precisely the condition a reconciliation is
supposed to end.

## Constraints carried from how this repository already works

- **Do not infer authority from reachability.** A branch existing, or a repository with the right
  tags being reachable, establishes nothing about which line is authoritative.
- **Do not merge or inspect casually.** `reconciliation/m3-corrected` gets the same branch-authority
  discipline every other line got: a durable boundary first — a clean tree and a commit that
  completes or pauses the work — then a narrow read-only delta, then a decision. Not a glance during
  unrelated work.
- **Neither line becomes authoritative by fiat**, and neither is discarded merely because it arrived
  concurrently. That is the rule that produced the four-way classification at `88b8f8a` and again in
  the [M3 reconciliation](../../evidence/2026-08-12-m3-reconciliation.md), and it applies here.
- **Freeze, do not delete.** A superseded line stays addressable, as `StandardsOrchestrator` did.

## Notes

Written as a decision rather than as "merge to main", because nothing in the repository establishes
that a merge is intended. The observable fact is the divergence; the disposition is a judgement the
owner has not recorded.

There is exactly one merge commit in this repository's history (`bc118b1`, a branch merge with no
pull-request reference), so this line was not developed through pull requests. `backlog-reconcile`
consequently reports its two pull-request-dependent checks as **NOT RUN** rather than as passing, and
that is the correct reading: whether this backlog agrees with what merged here is undetermined, not
verified. A zero-merge repository is not a reconciled one.

**Nothing on this line has been pushed.** Every commit from `0f27f5e` onward is local, so `origin`
does not yet know this line exists — which is a fact about the disposition question, not an
independent problem to solve first.
