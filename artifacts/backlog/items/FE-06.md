## What

Decide which development line is authoritative for this repository, reconcile the backlog claims that
disagree across lines, and only then decide what `main` should say.

**Re-scoped 2026-08-12.** This item was written as a two-branch question — `m3-scope-registry` versus
`main` — and that framing is now known to be wrong. A third line exists and is ahead of both, and the
lines disagree about a backlog claim rather than merely differing in commits. Publishing either side
before that disagreement is adjudicated would make branch movement decide a question nobody decided.

## Why

`main` describes an earlier repository than any working line. That was the original observation and it
remains true. What has changed is that "the working line" is no longer singular, so *choose what
`main` says* now contains a prior question: **which account is the record?**

The disagreement is substantive, not clerical. One line holds a parent epic closed; another holds the
same epic with open children carrying real evidence. A merge in either direction produces a backlog
that fails validation, and resolving it by whichever direction is merged second is not a decision.

## The durable requirement

This item is normative about **procedure**, not about any measurement. In order:

1. **Measure the live topology at decision time.** Current branch and full HEAD, working tree state,
   every local and remote ref, ahead/behind against each materially relevant line, worktrees and what
   they hold, and whether commits appeared since the last recorded checkpoint. A previously recorded
   count is evidence about that earlier moment and nothing else.
2. **Fetch before any remote claim.** Remote-tracking refs are stale until fetched. Ahead/behind
   against `origin/*` is not established by a measurement that did not fetch, and must not be reported
   as though it were.
3. **Identify every materially relevant line**, including any that this item does not name. The
   failure this re-scope corrects was reasoning from the two lines the item happened to mention.
4. **Reconcile conflicting backlog claims first.** Where two lines disagree about an item's status,
   adjudicate the claim on its evidence before choosing a branch. Never let merge order decide it.
5. **Then decide `main`.** Only once the resulting backlog is internally consistent.

**No ahead/behind count belongs in this body.** The original text carried one and it has been wrong
three times — see the evidence section. A number written into a decision item decays into an
assumption that outlives its measurement.

## Notes

Written as a decision rather than as "merge to main", because nothing in the repository establishes
that a merge is intended. The observable fact is divergence; the disposition is a judgement the owner
has not recorded. That remains true and is the reason this item exists at all.

There is exactly one merge commit in this repository's history (`bc118b1`, a branch merge with no
pull-request reference), re-verified 2026-08-12. This line was not developed through pull requests, so
`backlog-reconcile` reports its two pull-request-dependent checks as **NOT RUN** rather than as
passing. Whether this backlog agrees with what merged here is undetermined, not verified. A zero-merge
repository is not a reconciled one.

**Closing this item is not production readiness.** ST-07 is independent: there is still no
live-validated authoritative GitHub Actions enforcement root, and no branch disposition creates one.
