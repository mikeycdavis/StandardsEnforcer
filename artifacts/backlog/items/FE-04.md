## What

Put the GitHub adapter's two API shapes in front of a real ruleset instead of documented responses,
and find out whether the documented model matches reality.

## Why

M2 asserted every gate semantic against an injected platform. Nothing in this system had met a live
GitHub configuration, and the README named that as the weakest link and the prerequisite for calling
anything production-ready.

## Notes

**It found that M2's central mitigation does not work.** Every workflow in a repository runs as the
GitHub Actions app — including one the pull request adds — so binding a required check to
`integration_id: 15368` constrains nothing the attacker was not already able to do. Pull request #1
on `enforcer-m4-governed` deleted the call into the trusted reusable workflow, replaced it with a
local job named exactly the required context, and GitHub reported `MERGEABLE` / `CLEAN` with the
enforcement deleted.

Open, not complete, and the asymmetry is the reason: **the hole is proven, the patch is not.** The
remedy — GitHub's `workflows` ruleset rule, which names a repository, a path and a commit — is
asserted against an injected platform only. See [[ST-07]].

Two documented behaviours did hold up and are worth keeping: `404 Branch not protected` is a real
answer meaning no classic protection, and `rules/branches/{branch}` returns only actively enforced
rules, so a ruleset in evaluate mode is absent rather than present-and-inactive.

The fixtures are preserved deliberately. **Pull request #1 must not be merged — it is the artefact.**
