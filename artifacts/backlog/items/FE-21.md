> **This item puts its parent's completeness in question and does not answer it.** EP-01 is
> `COMPLETE` at 8/8, and its claim is that a pack's own evaluator runs under a pinned identity. The
> defect below is a case where the evaluator is never reached at all, for a repository the pack itself
> considers governed — so it is EP-01's claim that fails, not a new one. Whether EP-01 reopens, or
> this belongs elsewhere, is an owner disposition on the same footing as EP-04's. **Nothing here
> changes any parent's status.**

## What

StandardsEnforcer decides adoption by the existence of one filename:

```js
const POLICY_FILE = "project-policy.yml";              // scripts/enforce.mjs:55
const policyPath = path.join(target, POLICY_FILE);     // scripts/enforce.mjs:409
if (!existsSync(policyPath)) { … STATE.NOT_ADOPTED }   // scripts/enforce.mjs:410
```

FinancialStandards — the authority whose adoption this is meant to be detecting — admits two:

```js
const POLICY_MARKERS = ["project-policy.yml", "project-policy.yaml"];   // FinancialStandards@3627c6f:scripts/init.mjs:71
```

and its `check` places no filename restriction on `--policy` at all
(`FinancialStandards@3627c6f:scripts/standards.mjs:507`), so a `.yaml` policy is fully evaluable.

The marker set this repository recognises is therefore **narrower than the authority's**.

## The proposition

> A repository that FinancialStandards itself recognises as governed, via a policy filename
> FinancialStandards itself accepts, must not be classified by StandardsEnforcer as unadopted.

## Why this is a false negative and not a portability wrinkle

Two consequences, and the second is the one that earns the item:

1. **Invocation.** `{policy}` would be bound to a path that does not exist, and Financial fails
   closed — `standards check: no policy at …` (`scripts/standards.mjs:169`). Correct behaviour,
   wrong diagnosis: the operator is told there is no policy when there is one, spelled the other way.

2. **Adoption, which happens first and is worse.** Control never reaches the adapter.
   `scripts/enforce.mjs:410-421` returns `STATE.NOT_ADOPTED`, and where scope records the repository
   `IN_SCOPE` it selects the stronger message deliberately:

   > *"…is recorded in scope for these standards by \<reviewer\> on \<date\>, and contains no
   > project-policy.yml: it is governed and has not adopted"*

   That is a blockable finding against a repository that has adopted correctly, and the authority is
   never invoked to contradict it. An enforcement false negative — the INV-E1 failure class inverted:
   not an unknown condition reported as success, but a satisfied condition reported as delinquency.

## Falsifier

```text
repo/
└── project-policy.yaml
```

- FinancialStandards `init` → already governed (`POLICY_MARKERS`).
- StandardsEnforcer `enforce` → `NOT_ADOPTED`; with a recorded `IN_SCOPE` disposition, governed and
  delinquent.

The two disagree, which is what makes this earned independently of the adapter contract.

## Where the remedy goes

**At the one remaining discovery site, and nowhere else.** `enforce()` discovers exactly one policy
path from the authority-admitted marker set; everything downstream consumes that path unchanged.

The evaluator seam is already ready for this and must stay ignorant: PR #2 (`4e3ef37`) removed the
reconstruction, so `runOfficialEvaluator` takes `{ target, policyPath }` and binds what it is given —
asserted structurally by `test/adapter-policy-binding.test.mjs`, and demonstrated with a
`project-policy.yaml` supplied from an unrelated directory. **Do not teach the seam `.yml` versus
`.yaml`.** If a remedy needs to touch it, the remedy is wrong.

## Open questions the remedy must answer, not assume

- **Two markers present.** `project-policy.yml` and `project-policy.yaml` in the same root is
  ambiguous, and picking one silently is the class of quiet resolution this repository keeps
  refusing. It is a candidate `ENFORCEMENT_ERROR`, not a precedence rule.
- **Whose marker set is it.** Today the set is FinancialStandards'. It was read out of that pack's
  `init` — which is *convention*, not its published interface. If the set is to be per-pack it
  belongs in the adapter contract and is a schema change; if it is the enforcer's own, that must be
  stated rather than inherited by accident. **Neither is assumed here.**
- **Scope of the change.** `POLICY_FILE` also appears in two `NOT_ADOPTED` messages
  (`scripts/enforce.mjs:419-420`), which name a filename to an operator. What they should say when
  the set has more than one member is part of the remedy.

## Acceptance

- A repository whose only policy is `project-policy.yaml` is not reported `NOT_ADOPTED`, and reaches
  the authority.
- The same repository under a recorded `IN_SCOPE` disposition is not reported governed-and-delinquent.
- Both markers present resolves to a named, tested outcome rather than a silent choice.
- `runOfficialEvaluator` still contains no policy filename — the existing structural assertion stays
  green without amendment.
- The `.yml` path is unchanged, proved by the existing suite passing untouched.
