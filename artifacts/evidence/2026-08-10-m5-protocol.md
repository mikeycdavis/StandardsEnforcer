# M5 protocol — can an organisation root survive the pull request that defeated M2?

**Date:** 2026-08-10 · **Status:** written before execution, and blocked on two things only a human
can do · **Question:** does GitHub provide an enforcement root an ordinary governed pull request
cannot replace?

Written first, and deliberately. The expected-versus-observed discipline that caught the wrong seed
disposition in the acceptance-lock work only works if the expectation is recorded before the
observation exists. M4 followed it; this records M5's before anything is created.

## The claim under test

> An organisation ruleset that requires a specific workflow — named by repository, path and commit —
> cannot be satisfied by a governed pull request that deletes the legitimate invocation and emits a
> check of the same name.

If it holds, StandardsEnforcer has an empirically validated GitHub root. If it does not, the answer
is not a more elaborate description of status checks; the architecture needs a different root, and
that is a finding rather than a setback.

## Blocked on

**1. A disposable organisation, created by hand.** There is no API for it. `POST /admin/organizations`
is GitHub Enterprise Server only and returns `404` against github.com; `gh org` lists and nothing
more. It has to be created at <https://github.com/organizations/plan> on the Free plan.

The authenticated account is a member of one organisation, **Genu-Inc**. That is a real organisation
and is not being touched: an experiment whose whole content is *deleting enforcement and merging
anyway* does not belong in a production namespace, and the request was for a disposable one.

**2. `admin:org` on the token.** Current scopes are `gist, read:org, repo, workflow`. Organisation
rulesets cannot be created or read for rule evaluation without `admin:org`:

```bash
gh auth refresh -h github.com -s admin:org
```

**3. One risk that cannot be resolved before the org exists.** Whether the `workflows` ruleset rule is
available on a Free organisation is unverified. It was rejected on a personal account with `HTTP 422`,
which established that it is not a repository-level feature and nothing further. If a Free
organisation also rejects it, that is itself the M5 result — *the mechanism exists but not at a tier
this experiment can reach* — and it must be recorded as unvalidated rather than worked around.

## Intended configuration, recorded before application

```text
<org>/m5-trusted    hosts .github/workflows/standards-gate.yml, pinned by commit
<org>/m5-governed   the adversarial target; public; default branch main
```

Organisation ruleset, targeting `m5-governed`'s default branch:

```json
{
  "name": "m5-organisation-root",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] },
    "repository_name": { "include": ["m5-governed"], "exclude": [] }
  },
  "rules": [
    { "type": "workflows",
      "parameters": { "workflows": [
        { "repository_id": <m5-trusted id>,
          "path": ".github/workflows/standards-gate.yml",
          "ref": "refs/heads/main",
          "sha": "<40-hex>" } ] } },
    { "type": "required_status_checks",
      "parameters": {
        "required_status_checks": [
          { "context": "standards / machine-learning", "integration_id": 15368 } ],
        "strict_required_status_checks_policy": false } }
  ]
}
```

Both rules, on purpose. M4 established that the second alone is satisfiable by the pull request; the
experiment is whether the first repairs it.

## Cases, and what each would mean

| # | Configuration | Expected | If observed otherwise |
| --- | --- | --- | --- |
| 5.1 | Both rules; repository calls the pinned workflow | `rooted`, `authoritative: true`, merge allowed | The remedy does not work even in the honest case |
| 5.2 | **The M4 spoof**: PR deletes the invocation, adds a job named `standards / machine-learning` | **merge blocked** — the required workflow did not run | **The candidate remedy is falsified and GitHub Actions cannot root enforcement at all** |
| 5.3 | PR adds a *second* workflow emitting the name, keeping the legitimate call | merge allowed; the real one ran | Name collision defeats the pinned rule too |
| 5.4 | PR edits the pinned reference to another commit of the trusted workflow | merge blocked | The rule pins a path but not a commit |
| 5.5 | Enforcer reads the org ruleset | `rootedAt: ["organization"]`, `pinnedWorkflows` non-empty | The adapter's org-ruleset shape is wrong |
| 5.6 | `--require-organisation-root` against a repository-only rule | `GATE_CONFIG_INVALID` | The flag has never been exercised; this is its first live test |

Case 5.2 is the decisive one. It is the exact pull request that produced `MERGEABLE / CLEAN` in M4 —
same substitution, same check name — so the only variable between the two experiments is the root.

Case 5.6 matters independently: `--require-organisation-root` has been simulated since M2 and has
never met an organisation, so its own correctness is assumed rather than shown.

## Discipline

Each case records the intended configuration before applying it and the observed configuration after,
as JSON, with raw request and response bodies preserved and credential-scanned, under
`artifacts/evidence/m5-raw/`. Repositories and the ruleset are preserved after the run so the recorded
configuration can be inspected, and the adversarial pull requests are left **open and unmerged** —
they are the artefacts.

The limitation to be recorded whatever the outcome:

> The organisation and its repositories share an owner with the account running the experiment. This
> establishes separation from the governed pull request and from a repository administrator. It does
> not establish separation from an organisation owner, and organisation owners can change or delete
> the ruleset.

## Once M5 runs

Whatever it returns, one line in the README changes, and it will be one of:

> StandardsEnforcer has a live-validated authoritative GitHub enforcement root for GitHub Actions:
> an organisation ruleset pinning the implementation by repository, path and commit.

or

> GitHub Actions cannot root enforcement against a governed pull request by any mechanism this
> project has been able to validate. The architecture needs a producer the pull request cannot be.
